## 후보 수집 규칙 (roulette 공통)

세 경로로 후보를 모은다.

### A. 멘션 엔터티 — 기본 경로

`activity.entities` 의 `MentionEntity.mentioned` 에서 `Account{id, name}` 을 얻는다.
봇 자신(`activity.recipient.id`)을 제외하고 `id` 기준으로 중복을 없앤다.

가장 신뢰할 수 있는 경로다. AAD id 가 확정적으로 들어온다.

### B. 평문 `@이름` — 본인 포함용

**Teams 에서는 자기 자신을 @멘션 할 수 없다.** 자동완성에 본인이 안 나오므로
`@샘플2` 라고 쳐도 멘션 엔터티가 생기지 않고 평문으로 남는다.

> #### ⚠️ 완전일치는 이 테넌트에서 작동하지 않는다 (실측)
>
> 로스터 표시명이 **`한글이름 (English Name)`** 형식이다:
> `샘플2 (Echo Sample)`, `더미1 (Foxtrot Dummy)`, `테스터1 (Alpha Tester)` …
>
> 사용자가 치는 것은 `@샘플2` 이므로 완전일치로는 **절대 안 맞는다.**
> 처음 설계한 완전일치 규칙은 실제로 `로스터 일치 0명` 으로 실패했다.

그래서 표시명에서 **별칭 집합**을 만들어 매칭한다.

`더미1 (Foxtrot Dummy)` →
`{'더미1 (jeong choi)', '더미1(jeongchoi)', '더미1', 'jeong choi', 'jeongchoi'}`

1. 별칭 **완전일치** 로 1명 → 채택
2. 없으면 별칭 **접두사 일치** 로 1명 → 채택
3. 어느 단계든 0명 또는 2명 이상 → **채택하지 않고 무시했다고 응답에 명시**

실측 로스터 10명으로 검증한 결과:

| 입력 | 결과 |
|---|---|
| `@샘플2` | ✅ `샘플2 (Echo Sample)` (완전일치) |
| `@더미1` | ✅ `더미1 (Foxtrot Dummy)` (완전일치) |
| `@echo` | ✅ `샘플2 (Echo Sample)` (접두사) |
| `@이` | ❌ 3명 모호 (테스터1·테스터2·테스터3) → 무시 |
| `@김` | ❌ 2명 모호 (샘플1·샘플2) → 무시 |
| `@없는사람` | ❌ 로스터에 없음 → 무시 |

동명이인은 조용히 추측하지 않고 무시하고 알린다.

### B-2. 멘션이 공백 단위로 쪼개진다 (실측)

표시명에 공백이 있으면 **Teams 가 멘션을 토큰마다 나눠서 보낸다.**
`더미1 (Foxtrot Dummy)` 한 명을 태그했을 때 실제로 온 것:

```
text: `<at>당첨자뽑기</at> <at>더미1</at> <at>(Foxtrot</at> <at>Dummy)</at> @샘플2 1명`
entities:
  mention name=`더미1`   id=29:USER-MRI…
  mention name=`(Foxtrot` id=29:USER-MRI…   ← 같은 id
  mention name=`Dummy)`  id=29:USER-MRI…   ← 같은 id
```

**대응 두 가지:**

1. `id` 기준 중복 제거 — 안 하면 1명이 3명으로 집계된다
2. 표시명은 엔터티(`더미1`)가 아니라 **로스터에서** 가져온다 (`더미1 (Foxtrot Dummy)`)

엔터티의 `name` 을 그대로 쓰면 이름이 잘린 채 남는다.

### C. 전원 모드

`@모든 사용자` / `@everyone` / `@전원` 이 들어오면 **로스터 전체**(봇 제외)를 후보로 쓴다.
이 경우 A·B 를 무시한다.

> ### ⚠️ `@everyone` 은 봇에 지원되지 않는다 (공식 확인)
>
> Microsoft 문서 원문:
> *"Agents in group chats enable user mentions using `@mention`; however, they don't support `@everyone` for mentions."*
>
> 같은 문서에 채널/팀 멘션은 애초에 봇에 **전달되지 않는다**고도 나온다.
> *"agents won't receive messages when the team or channel is mentioned"*
>
> 즉 `@모든 사용자` 가 멘션 엔터티로 올지, 평문으로 올지, 아예 안 올지 **문서로는 확정할 수 없다.**
> 다행히 어느 쪽이든 로스터 조회로 우회된다 — 로스터 접근은 문서에 보장돼 있다:
> *"it has access to metadata about the conversation, such as the list of conversation members"*
>
> ### ✅ 실측 결과 (2026-08-20, 실제 그룹 채팅)
>
> `@당첨자뽑기 @모든 사용자 2명` 을 보냈을 때 실제로 온 것:
>
> ```
> text: `<at>당첨자뽑기</at> <at>모든 사용자</at> 2명`
> mention name=`모든 사용자`
>         id=`29:EVERYONE-PSEUDO-ID-NOT-IN-ROSTER…`
> ```
>
> **확정된 것:**
>
> 1. `@모든 사용자` 는 **멘션 엔터티로 도착한다** (평문 아님)
> 2. 그대로 두면 **후보 1명**으로 집계된다
> 3. **id 형태로는 실제 사용자와 구분할 수 없다.** 둘 다 `29:` + 긴 문자열이다:
>    - 전원: `29:EVERYONE-PSEUDO-ID…`
>    - 실제 사용자(더미1): `29:REAL-USER-MRI…`
> 4. `get_members()` 는 **봇을 포함하지 않는다** (10명 반환, 봇 제외 후에도 10명)
>
> **그래서 감지 규칙은 이렇게 확정한다:**
>
> 1. **주 경로** — 멘션 id 가 **로스터에 없고, 이름이 전원 표현**(`모든 사용자` / `everyone` /
>    `전원` / `모두` / `all`)이면 전원 모드.
>    ⚠️ **봇은 먼저 제외한다** (id 가 `28:` 로 시작). 봇은 로스터에 없으므로,
>    제외하지 않으면 봇 멘션만으로 전원 모드가 켜진다.
> 2. **보조** — 원본 텍스트에서 전원 표현을 **태그 형태로만** 찾는다
>    (`@모두`, `<at>모든 사용자</at>`). `모든 사용자` 는 공백을 포함하므로 `split()` 으로는 못 잡는다.
>
> 전원 모드로 판정되면 그 엔터티를 후보로 세지 않고, **로스터 전체**로 교체한다.
> 그리고 판정 근거를 응답에 표시해 조용히 넘어가지 않게 한다. 근거는 로그(`후보 판정 …`)에도 남긴다.
>
> **2026-10-27 오판** — `@당첨자뽑기 @최정 @이태호 @투표만들기` 가 전원 11명 추첨이 됐다.
> 당시 규칙은 "로스터에 없는 멘션 = 전원" 이었고, **우리 봇만** 제외했다. 다른 봇(`@투표만들기`)도
> 로스터에 없어서 전원으로 오인했다. 그래서 바꿨다:
>
> - **모든 봇**(`28:`)을 전원 판정과 후보에서 뺀다. 판에 "봇이라 후보에서 뺐습니다" 안내
> - 로스터에 없는 멘션은 **이름까지 전원 표현일 때만** 전원이다. 그 밖(태그 그룹 등)은 빼고 안내한다.
>   틀리면 판이 넓어지지 않고 좁아지는 쪽이라 더 안전하다
> - 텍스트 보조 신호를 태그 형태로 좁혔다. 부분문자열로 찾으면 "다들 **모두** 모여요",
>   이름 "**All**en" 도 전원 모드가 된다

## roulette-agent — `@당첨자뽑기`

### 무엇을 하는가

후보 중 **당첨자 n명**을 뽑는다. 단, 결과를 한 번에 알려주지 않는다.
**생존자를 한 명씩 공개하며 후보 풀을 줄여나가고**, `n+1` 명이 남았을 때
마지막 라운드에서 **당첨자를 한 명씩** 공개한다. 끝까지 불리지 않은 1명이 마지막 생존자다.

풀이 줄어들 때마다 남은 사람의 당첨 확률이 올라가므로 긴장이 누적된다.

장치가 두 가지 있다. **반전**(공개된 생존자가 다시 후보로 끌려 내려간다)과
**🃏 1등이대신당첨**(가상 후보. 뽑히면 생존 1등이 대신 당첨). 아래 각 절 참고.

### 입력

```
@당첨자뽑기 @A @B @C @D @E 2명
@당첨자뽑기 @모든 사용자 3명
@당첨자뽑기 @A @B @샘플2            ← 본인은 평문, n 생략 시 1명
@당첨자뽑기 @A @B @C 1명 조커없이    ← 🃏 을 빼고 뽑는다
```

- 당첨자 수 `n` : 텍스트 끝의 `(\d+)\s*명?` 을 우선 해석. 없으면 **1**
- `조커없이` (`조커 없이`) : 🃏 1등이대신당첨 을 후보에 넣지 않는다

### 진행 규칙

후보 `N` 명, 당첨자 `n` 명일 때 **생존자를 한 명씩 공개**한다.

```
공개할 생존자 = N - n 명
마지막 단계에서 당첨자 n명을 한 명씩 공개 → 남은 1명이 마지막 생존자
```

총 생존자 `N-n` 명, 총 당첨자 `n` 명. 합이 `N` 이라 누구도 미공개로 남지 않는다.

단계 수가 `MAX_STEPS` (12) 를 넘으면 앞쪽 단계에서 생존자를 **묶어서** 공개한다.
후보 30명을 한 명씩 가면 연출이 2분을 넘어가 지루해진다.
당첨자 공개도 `MAX_WINNER_REVEALS` (3) 회를 넘으면 앞쪽 공개에서 **묶는다**.

### 워크스루 (N=5, n=2)

| 단계 | 남은 후보 | 공개 |
|---|---|---|
| 1/3 | 5 | 생존자 1명 → 4명 남음 |
| 2/3 | 4 | 생존자 1명 → 3명 남음 (= n+1) |
| 3/3 (마지막) | 3 | **당첨자 1명** → **당첨자 1명** → 남은 1명이 마지막 생존자 |

## 연출 규칙

### 메시지는 **딱 한 개**다

연출 전체가 **메시지 하나를 계속 편집**하는 방식으로 진행된다.

**왜** — 1분 안에 메시지가 20개씩 올라오면 채팅방이 업무에 방해가 된다.
편집은 새 메시지 알림을 만들지 않으므로, 보고 싶은 사람만 그 메시지를 지켜보면 된다.

거절·오류 안내만 별도 메시지로 나간다 (그 자체로 대화가 끝나므로).
그리고 끝에 **당첨자 알림 메시지가 하나** 더 나간다 (아래).

### 사람은 **@태그하지 않는다** — 당첨자만 예외

이름은 `**볼드 평문**` 으로만 표시한다.

**왜** — 알림 개수를 줄이는 것이 목적이다. 추첨 한 번에 10명을 태그하면
전원에게 알림이 가서 정확히 피하려던 방해가 발생한다.

**예외 — 당첨자 알림.** 결과 화면을 한 박자 보여준 뒤, **당첨자만** @태그한 짧은 메시지를
새로 보낸다 (`🎉 당첨 @A, @B`). 알림은 당첨자에게만 간다.

- 판(카드)을 편집하면서 멘션을 넣지 않는다. **편집에 추가된 멘션으로 알림이 가는지는 확인하지 못했다.**
  새 메시지의 멘션은 알림이 간다
- 🃏 이 뽑혔으면 대신 당첨된 사람을 태그한다. 🃏 은 태그하지 않는다
- 전원 당첨도 그 안내 메시지 하나에서 전원을 태그한다
- 이 메시지 전송이 실패해도 추첨은 끝난 것이라 "추첨 중 오류" 안내를 띄우지 않는다 (로그만 남긴다)

### 판은 Adaptive Card 다

평문 메시지로는 **글자를 크게 할 수 없다.** 공식 지원 표에서
`Header (levels 1–3)` 은 text-only 메시지 ❌ / 리치 카드 ✔️ 이고, 평문에서 쓸 수 있는 것은
굵게·기울임뿐이다.

대사 줄만 키우려면 카드가 필요하다. 그래서 판을 Adaptive Card 로 두고
**대사 TextBlock 만 `size="Large"`** 로 만든다. 나머지 줄은 기본 크기다.

### 메시지 템플릿

```
🎲 **당첨자뽑기** · 후보 10명 · 당첨 2자리 · 진행 🧙 **마법사**   ← 불변 (헤더)
(참여자 안내가 있으면 여기 한 줄)                ← 불변

▸ **3/8번째 뽑는중**                          ← 진행 상태
▸ 생존 **예시2**, **테스터2**, **가상1**        ← 지금까지의 생존자
▸ 당첨 **더미1**                               ← 공개된 당첨자 (있을 때만)
▸ ▰▰▰▱▱▱▱▱ 완료 3/8                          ← 진척

🧙 수리수리… 두구두구…                          ← 진행자 대사
다시 뽑으려면 **@당첨자뽑기** 를 …              ← 결과 화면에만
```

| 필드 | 가변 | 내용 |
|---|---|---|
| 헤더 | 불변 | `당첨자뽑기` + 후보 수 + 당첨 자리 수 + 진행자 (+ 참여자 안내) |
| 진행 상태 | 가변 | `x/n번째 뽑는중` (`반전!`) → `당첨자 뽑는중` (`당첨자 k/m 뽑는중`) → `종료됨` |
| 생존자 | 가변 | 지금까지 살아남은 사람을 `, ` 로 나열 (20명 초과 시 `+N명`). 결과 화면에서는 `생존 순서` |
| 당첨 | 가변 | 지금까지 공개된 당첨자. 당첨자 공개가 시작되면 나타난다 |
| 진척 | 가변 | 진행 바 + `x/n` |
| 대사 | 가변 | 도입 / 두구두구 / 발표 / 뜸들이기 / 당첨 문구. **이 줄만 `size="Large"`** |
| 다시 부르기 | 결과 | 결과 화면에만 작게 |

🃏 이 후보에 들어가면 헤더가 `후보 **10명** + 🃏` 가 되고 안내 줄이 하나 붙는다.

남은 확률 줄(`남은 7명 중 2명 당첨 · 1인당 29%`)을 넣었다가 뺐다 (2026-10-27).
대사 줄에 비해 글자가 작아 눈에 띄지 않았다.

**왜** — 각 메시지를 다 읽어야 현황을 아는 방식은 눈에 들어오지 않는다.
같은 자리에 고정된 판을 두고 값만 바뀌면 지금 상황이 한눈에 보인다.

### 진행자 — 판마다 한 명이 대사를 맡는다

요청마다 진행자를 한 명 정하고, 그 판의 대사는 모두 그 진행자의 말투로 나간다.
같은 문구를 여러 판 보다 보면 "또 그 말" 이 된다. 진행자가 바뀌면 판마다 결이 달라진다.

| 진행자 | 말투 | 예 |
|---|---|---|
| 🧛 뱀파이어 · 🤖 로봇 | 무덤덤하게 살살 긁는다 | "**더미1**님이 생존이라니 믿을 수 없어." · "당첨을 축하드립니다 ^^" |
| 🧙 마법사 · 💩 똥 | 약간 유순한데 얄미운 어린이 | "**더미1**님이 생존했어!" · "당첨 축하해!!" |
| 🧝 엘프 · 🦹 악당 | 존댓말 (예전 기본 말투) | "**더미1**님, 긴장되시나요?" · "축하합니다!" |

- **과장하지 않는다.** 듣는 사람이 직장인이라 유치하면 안 되고, 살짝 어설픈 정도가 맞다 (사용자 결정)
- 같은 말투의 진행자는 같은 문구 풀을 쓴다. 진행자마다 다른 것은 이모지·이름·시작 인사·두구두구 효과음
- 같은 대화방에서 **직전 판의 진행자는 다시 고르지 않는다**
- 대사의 말머리는 `진행자 이모지:` 다 (`🤖: 삐빅. 진행 시작.`). 말하는 사람이 보이게 한다. 상태가 바뀌는 순간(🎯 당첨, ⚡ 반전, ⬇️⬆️ 자리 바꿈, 🃏, 🎉 결과)만
  그 표시를 말머리로 쓴다. 판을 훑어볼 때 그 순간이 보여야 한다
- 이모지는 **성별 표시가 없는 것**을 쓴다. 🦹‍♀️ 같은 합성 이모지는 클라이언트에 따라 둘로 쪼개져 보일 수 있다
- 전원 당첨은 연출이 없어서 진행자도 없다

**이름 뒤에는 늘 `님`** — 대사 속 이름은 `**더미1**님` 으로 고정한다. 그래서 문구의 조사는
받침이 있는 쪽(`이/은/을`)만 쓰면 되고, 이름마다 받침을 따질 필요가 없다.
문구에 `{name}님` 을 다시 쓰거나 `는/가/를` 을 붙이면 테스트가 막는다.
판의 생존·당첨 줄과 결과 화면의 당첨자 나열은 대사가 아니라 목록이라 님을 붙이지 않는다.

### 단계는 앞쪽은 빠르게, 끝쪽은 느리게

한 번에 결과가 나오면 긴장이 생기지 않는다. 대사 풀을 나눠서 여러 번 편집한다.
다만 모든 단계가 같은 호흡이면 앞쪽에서 지루해진다. 그래서 단계 위치에 따라 박자가 다르다.

```
앞쪽 탈락 단계   두구두구 → 발표
끝쪽 2단계       도입 → 미니 뜸 → 두구두구 → 발표
마지막 단계      뜸들이기 3~5회 → 도입 → (두구두구 → 당첨 공개) × 당첨 묶음 수 → 결과
```

```
1) 도입      "이번에 살아남을 사람은 누구일까요?"
2) 미니 뜸   "**가상1**!!!!! 아 아닙니다"
3) 두구두구   "두구두구두구…"
4) 발표      "**예시2** 님이 살아남았습니다!"
```

각 박자의 문구는 진행자 말투의 **별도 풀**에서 뽑는다 (`lines.py`). 같은 문구가 연속으로
나오지 않도록 (진행자, 박자) 마다 셔플 덱을 쓴다. 이 문서의 대사 예시는 엘프 말투다.

**미니 뜸**은 아직 미공개인 사람 중에서 부르되, **이번 단계에 발표될 사람은 뺀다.**
"X! …아닙니다" 바로 뒤에 "X 생존" 이 뜨면 농담이 깨진다. 부를 사람은 추첨 계획을 짤 때 정한다.

### 마지막 단계는 뜸을 들이고 당첨자를 한 명씩 부른다

마지막 단계에서는 **남아 있는 후보 중 한 명의 이름을 랜덤으로 불러 놓고 농담으로 돌린다.**
`3~5회` 반복한 뒤 당첨자를 공개한다.

```
🥁 **더미1**!!!!! …일까요? (농담)
🥁 **더미2**!!!!! 아 아닙니다
🥁 **테스터3**… 인 줄 알았죠?
   … 3~5회
🥁 자, 마지막입니다. 숨을 참으세요.
🥁 두구두구두구…
🎯 (1/2) 당첨은… **더미2** 님!
🥁 드르르르르륵…
🎯 (2/2) **테스터3** 님, 당첨!
🎉 **당첨** **더미2**, **테스터3**        ← 결과 화면
```

이름을 부르는 대상은 **아직 후보에 남아 있는 사람**(n+1명) 중에서 고른다.
이미 생존이 확정된 사람을 부르면 농담이 성립하지 않는다.

**왜 생존자가 아니라 당첨자를 부르는가** — 예전에는 마지막 생존자를 발표한 뒤 당첨자를 띄웠다.
1명 추첨에서는 2명 중 생존자가 불리는 순간 당첨자가 정해져서, 정작 당첨 화면은 확인일 뿐이었다.
정점이 당첨자 공개에 오도록 순서를 바꿨다.

### 반전 — 공개된 생존자를 다시 끌어내린다

탈락 단계 중간에 한 번, 이미 공개된 생존자 1명을 **다시 후보로 끌어내리고**,
아직 안 불린 비당첨자 1명이 **그 자리(생존 순서의 같은 위치)를 차지한다.**

```
⚡ 잠깐! 반전입니다!
⬇️ **더미1** 님… 생존 취소! 다시 후보로!
⬆️ 빈자리에 **더미2** 님이 올라갑니다!
```

| 규칙 | 값 | 이유 |
|---|---|---|
| 발동 | **항상** (`SWAP_CHANCE` 1.0) | 2026-10-27 사용자 결정. 처음엔 0.5 였다. 시점과 대상이 매번 달라서 그것으로 흔든다 |
| 시점 | 탈락 단계의 **40~60%** 구간에서 흔든다 | 고정하면 시점을 학습한다 |
| 횟수 | 한 판에 최대 1회 | |
| 조건 | 마지막 단계 전에 공개되는 생존자가 있을 때 (`후보 - 당첨 ≥ 2`) | 끌어내릴 사람이 없다 |

끌려 내려간 사람은 다시 후보다. **결국 당첨될 확률은 그 시점에 남은 다른 후보와 같다**
(`n / 남은 인원`). 늘 당첨되거나 늘 다시 살아남으면 "끌려 내려오면 당첨" 처럼 금방 읽힌다.
당첨된다면 그 사람은 앞에서 생존자인 척 공개된 것이다.
다시 살아남는다면, 차지한 사람이 원래 공개될 자리에서 대신 공개된다.

반전 뒤 생존자에 "확정" 같은 표시는 하지 않는다 (사용자 결정).

### 🃏 1등이대신당첨 — 가상 후보

후보에 **가상 참여자 `1등이대신당첨`** 을 함께 넣는다. 이것이 당첨되면
**끝났을 때의 생존 순서 1등**(가장 먼저 살아남은 사람)이 대신 당첨된다.

```
🎯 **1등이대신당첨** 님, 당첨!
🃏 1등이 대신 당첨됩니다! 생존 1등은…
🎯 가장 먼저 살아남았던 **예시1** 님이 당첨입니다!
```

- 기본으로 넣는다. 메시지에 `조커없이` 가 있으면 뺀다 (발표자 정하기처럼 진지한 용도)
- 전원 당첨(`n == N`)이면 넣지 않는다. 대신 받을 생존자가 없다
- 후보 30명 상한에는 세지 않는다
- 반전으로 1등 자리가 바뀌면 바뀐 사람이 1등이다. 첫 단계가 묶음 공개면 그 첫 이름이다
- 뜸들이기·미니 뜸·반전에서도 보통 후보처럼 불릴 수 있다

**공정성** — 실제 후보 N명 + 🃏 중 n자리를 뽑는다. 🃏 자리는 생존 1등에게 가고,
생존 순서는 무작위라 누가 1등일지는 모두 같다. 실제 당첨자는 언제나 n명이고
사람마다 확률은 그대로 **n/N** 이다 (테스트에서 분포로 확인).

### 진행 속도 — 대기는 매번 흔든다

고정 대기를 쓰면 몇 라운드 만에 "이만큼 기다리면 다음 대사가 뜬다" 는 것을
무의식중에 학습해 버려서 긴장이 사라진다. 매 박자마다 범위에서 새로 뽑는다.

| 박자 | 대기 범위 |
|---|---|
| 도입 | 1.5 ~ 2.7초 |
| **두구두구** | **곡선** — 첫 단계 1.5 ~ 2.8초 → 당첨 공개 2.7 ~ 4.4초 |
| 발표 | 1.0 ~ 1.5초 |
| 뜸들이기 1회 | 1.5 ~ 3.1초 |

2026-10-27 기다리는 대사(도입·두구두구·뜸들이기·시작 인사)만 (+0.5, +1.0)초 늘렸다.
한 마디 한 마디가 너무 빨리 지나간다는 피드백. 발표(생존·당첨·자리 바꿈)는 원래 길이다.

두구두구는 뒤로 갈수록 길어진다. 곡선 위에서도 범위로 흔든다 — 곡선만 두면 그 곡선을 학습한다.

⚠️ **최소값은 1.0초 이상을 유지한다.** 이 대기가 곧 편집 API 호출 간격이므로
더 짧아지면 Teams 대화방 전송 한도에 가까워진다 (실측 0.7회/초).
앞쪽을 빠르게 하는 방법은 대기를 줄이는 것이 아니라 **박자를 빼는 것**이다 (앞쪽 단계의 도입).

예상 소요 (`estimated_bounds`). 같은 조건에서도 매번 다르게 걸린다.

| 후보 / 당첨 | 소요 |
|---|---|
| 5명 / 1명 | 약 27~54초 |
| 10명 / 2명 | 약 43~81초 |
| 30명 / 1명 | 약 52~95초 |

### 이름 표시

표시명이 `한글이름 (English Name)` 형식이라 8명을 나열하면 판이 넘친다.
판과 대사에서는 **괄호 앞부분만** 쓴다 (`더미1 (Foxtrot Dummy)` → `더미1`).
괄호가 없는 이름은 그대로 둔다.

### 자동완성 항목 — 표시와 삽입을 분리한다

`@당첨자뽑기` 를 입력하면 자동완성 메뉴가 뜬다. 기본 동작(`type: "basic"`)은
**`title` 을 그대로 입력창에 붙여넣는 것**이라, title 에 `@당첨자뽑기` 가 들어 있으면
이미 입력한 멘션에 **또 붙어서 중복**된다.

`type: "prompt"` 로 두면 나뉜다:

| 필드 | 값 | 역할 |
|---|---|---|
| `title` | `@당첨자뽑기 @홍길동 @김철수 2명` | 메뉴에 **표시** (그대로 유지) |
| `description` | 설명 | 메뉴에 **표시** |
| `prompt` | `@홍길동 @김철수 2명` | 선택 시 **삽입** (에이전트 멘션 제외) |

공식 문서: *"When a user selects a prompt starter, Teams inserts its `prompt` value
into the user's compose box."*

### 엣지 케이스

| 조건 | 동작 |
|---|---|
| `n < 1` | 거절. 사용법 안내 |
| `n > N` | 거절. "후보가 N명인데 n명을 뽑을 수 없다" |
| `n == N` | 연출 없이 즉시 "전원 당첨" 공개 (생존자가 없다) |
| `N == n + 1` | 단계 1회 → 곧바로 마지막 단계 |
| `N < 2` | 거절. 후보 2명 이상 필요 |
| `N > 30` | 거절 |
| 후보 없음 | 사용법 안내 |
| 평문 `@이름` 이 로스터에 0명/2명+ 매칭 | 그 토큰만 무시하고, 헤더에 무시했다고 표시 |
| 진행 중 재호출 | "이미 진행 중" 거절 |
| 같은 사람 중복 태그 | `id` 로 중복 제거 |
| 전원 모드인데 로스터 조회 실패 | 원인을 알려주고 거절 (조용히 0명으로 두지 않는다) |

### 공정성

- `SystemRandom().sample(candidates, n)` 으로 **연출 시작 전에** 당첨자를 확정한다 (🃏 포함 시 N+1명 중)
- 생존자 공개 순서는 비당첨자를 셔플한 결과
- 반전과 🃏 대신 당첨도 확정된 결과에 맞춘 공개 순서일 뿐이다
- 연출 중 결과가 바뀌는 경로는 없다. 재추첨도 없다

## vote-agent — `@투표만들기`

### 투표 하나당 메시지 **한 개**

생성 폼 → 투표판 → 마감판이 **모두 같은 activity** 다. roulette 과 같은 원칙이다.

```
@투표만들기            → 폼 카드 게시           (메시지 1개 생성)
  ↓ 제출              → 같은 메시지를 투표판으로 갱신
  ↓ 누군가 클릭         → 같은 메시지 갱신 (전원 화면 반영)
  ↓ 마감              → 같은 메시지를 마감판으로 갱신
```

별도 요약 메시지를 게시하지 않는다. 마감판 자체가 결과다.
거절·오류 안내만 별도 메시지로 나간다.

### 생성 — 구분자를 쓰지 않는다

처음에는 `제목 / 항목1, 항목2 / 마감` 처럼 `/` 를 구분자로 썼는데 실패했다.

| 쓰고 싶은 것 | 옛 문법에서 |
|---|---|
| `9/10(목) 회식 메뉴 선정` | 제목이 `9` 와 `10(목) 회식 메뉴 선정` 로 쪼개진다 |
| `땡땡식당 (https://naver.me/xxx)` | 링크의 `//` 에서 쪼개진다 |

`#`, `!`, `|` 로 바꿔도 같은 문제가 반복된다. **제목과 항목에는 어떤 문자든 들어갈 수 있다.**

그래서 **줄바꿈**을 구조로 쓴다. 줄바꿈은 제목이나 URL 안에 들어갈 수 없으므로
충돌이 구조적으로 불가능하다.

```
@투표만들기 9/10(목) 회식 메뉴 선정          ← 첫 줄 = 제목 (문자 제약 없음)
땡땡식당 (https://naver.me/GdymUOVY)        ← 각 줄 = 항목 하나 (URL 자유)
무슨식당 (https://naver.me/Fk738sTW)
초밥집
마감: 금요일 18시                            ← 지시어 (생략 가능)
복수                                        ← 지시어 (생략 가능)
```

Teams 에서는 **Shift+Enter** 로 줄을 바꾼다.

| 줄 | 해석 |
|---|---|
| 첫 줄 | 제목 |
| `마감: …` / `마감일: …` / `deadline: …` | 마감 시각 |
| `복수` / `복수선택` / `다중` / `multi` | 복수 선택 허용 |
| 그 외 모든 줄 | 항목 하나 |

### 제목만 오면 폼을 연다 — 파싱 위험 0

항목 줄이 없으면 **아무것도 추측하지 않고** 입력 폼을 띄운다. 제목은 미리 채워 둔다.

```
@투표만들기 9/10(목) 회식 메뉴 선정      → 제목이 채워진 폼이 열린다
@투표만들기                              → 빈 폼이 열린다
```

이 설계에는 중요한 성질이 있다 — **Teams 가 줄바꿈을 삼켜서 한 줄로 보내더라도
잘못 해석되지 않고 이 경로로 떨어진다.** 최악의 경우가 "폼이 열린다" 이므로
조용히 엉뚱한 투표가 만들어지는 일이 없다.

폼은 카드 안의 입력 필드다 (다이얼로그가 아니다). 다이얼로그를 쓰면 버튼 카드 +
다이얼로그로 왕복이 늘어나는데, 인라인 입력은 같은 메시지에서 끝난다.
Adaptive Card 입력값은 보는 사람마다 따로 유지되므로 여럿이 봐도 섞이지 않는다.

| 필드 | 설명 |
|---|---|
| 제목 | 필수, 최대 80자 |
| 항목 | 필수, **한 줄에 하나씩**, 2~10개, 각 60자 |
| 마감 | 비우면 마감 없음 |
| 복수 선택 허용 | 토글 |

검증에 걸리면 **폼을 그대로 유지하고 오류만 얹는다.** 입력한 값은 보존된다.

**항목 분리는 줄바꿈이 우선이다.** 여러 줄이면 줄 단위로만 나누고 쉼표로 재분할하지
않는다 — `땡땡식당 (강남, 2호점)` 같은 이름이 깨지기 때문이다. 한 줄일 때만 쉼표로 나눈다.

### 옛 `/` 문법 마이그레이션

옛 문법으로 보이면 **바로 만들지 않고** 값을 폼에 옮겨 담고 안내를 띄운다.
추측이 틀려도 사용자가 폼에서 고치면 되므로 손해가 없다.

```
@투표만들기 회식장소 / 삼겹살, 치킨, 초밥 / 금요일 18시 / 복수
  → 폼: 제목=회식장소, 항목=삼겹살/치킨/초밥(줄바꿈), 마감=금요일 18시, 복수=켜짐
    ℹ️ 이제 `/` 구분자를 쓰지 않습니다. …
```

판별 기준은 **항목 자리에 쉼표가 있는가**다. 그래서 `9/10(목) 회식 메뉴 선정` 처럼
날짜가 든 제목은 옛 문법으로 오해하지 않는다.

### 마감 표현 (LLM 없이 정규식)

| 입력 | 해석 (8/20 목 14:30 기준) |
|---|---|
| `18시`, `18:00` | 8/20(목) 18:00 |
| `10시` | 8/21(금) 10:00 — 이미 지났으니 다음 날 |
| `오후 6시`, `저녁 7시` | 8/20(목) 18:00 / 19:00 |
| `금요일 18시` | 8/21(금) 18:00 |
| `목요일 10시` | 8/27(목) 10:00 — 오늘이지만 지났으니 다음 주 |
| `내일 14시 30분`, `모레 9시` | 상대 날짜 |
| `8/22 18:00`, `8월 22일 18시` | 절대 날짜 |
| `2026-09-01 09:00` | 절대 날짜 |
| `3시간`, `30분`, `2일` | 상대 시간 |
| (빈 값) | 마감 없음 |

**애매하면 오류로 돌린다.** 엉뚱한 시각으로 조용히 마감되는 것이 더 나쁘다.
`아무말`, `25시`, `13/45`, `0분` 은 모두 거절한다.

지난 날짜의 연도 이월은 **60일** 기준이다. 12월에 `1/5` 는 내년이 맞지만,
8/20 에 `8/19` 는 오타일 가능성이 크므로 거절한다.

시각은 KST 로 해석하고 **UTC 로 저장**한다.

### 투표판

```
📊 **회식 장소**
진행 중 · 8/21(금) 18:00 마감 · 복수 선택 가능

**1. 삼겹살**  ▰▰▰▰▰▰▰▱▱▱  **4표** · 67%
더미1, 테스터3, 샘플1, 가상1
**2. 치킨**  ▰▰▰▱▱▱▱▱▱▱  **2표** · 33%
더미1, 예시2
**3. 초밥**  ▱▱▱▱▱▱▱▱▱▱  **0표** · 0%
—

총 **7표** · **6명** 참여 · 만든 사람 샘플2

[삼겹살]  [치킨]  [초밥]     ⋯ [투표 마감하기]
```

- 막대는 **참여자 수**를 기준으로 채운다 — "참여자 중 몇 명이 이걸 골랐나"

  > ⚠️ 처음에는 **최다 득표(top)** 를 분모로 썼는데, 그러면 1위 항목이 1표든 10표든
  > 항상 꽉 찬 상태이고 0표는 항상 빈 상태다. 후보 2~3개에 표가 몇 개뿐인 실제
  > 상황에서는 **막대가 고정돼 보였다.** 참여자 기준으로 바꾸니 표가 하나 들어올
  > 때마다 모든 막대가 움직인다. 복수 선택에서도 한 항목의 득표는 참여자 수를
  > 넘을 수 없으므로 항상 0~100% 다.

- 퍼센트를 함께 적는다. 막대 10칸은 해상도가 낮아 한 표 차이가 안 보일 수 있다
- **백틱(코드 스팬)으로 감싸지 않는다.** Teams 가 배경 박스를 그려서 0% 일 때
  빈 막대가 오히려 채워진 것처럼 보였다. `▰`/`▱` 은 폭이 같아 정렬도 유지된다
- 이미지 없이 유니코드 블록이라 어디서나 같게 보인다
- **각 항목 아래에 투표자 이름을 나열한다.** 전원이 볼 수 있다
- 이름은 `한글 (English)` 의 앞부분만 쓴다 (`더미1 (Foxtrot Dummy)` → `더미1`)
- 사람을 **@태그하지 않는다** — 알림을 줄이는 것이 목적이다
- `투표 마감하기` 는 `mode: secondary` 라 오버플로 메뉴로 밀려 투표 버튼과 섞이지 않는다

마감판은 버튼이 사라지고 1위에 🏆 가 붙는다. 동표면 `공동 1위` 로 여럿을 표시한다.
표시 시각은 예정 시각이 아니라 **실제로 닫힌 시각**이다.

### 실시간 반영

1. 옵션 클릭 → `Action.Execute` → `@app.on_card_action_execute("vote")`

   > ⚠️ 라우팅은 `verb` 가 아니라 **`data["action"]`** 으로 이루어진다.
   > `verb` 만 넣으면 매칭이 안 되고, Teams 는 "응답이 앱으로 전송되었습니다" 만
   > 띄운 뒤 카드가 갱신되지 않는다. 버튼이 잠깐 비활성화됐다 풀리므로 성공처럼 보인다.
   > 실제로 이 누락으로 투표·마감이 전부 동작하지 않았다.

2. 투표별 `asyncio.Lock` 안에서 SQLite read-modify-write
3. DB 상태로 카드 재구성
4. `ctx.api.conversations.activities(conv_id).update(activity_id, card)` → **전원 화면 갱신**
5. 클릭한 사람에게는 invoke 응답으로 짧은 확인 (`'라면' 에 투표했습니다`) — 채팅방에는 남지 않는다

단일 프로세스 + 투표별 락이라 동시 클릭 경합이 구조적으로 없다.

> Adaptive Card `refresh` / `userIds` 의 **60명 제한은 이 방식에 걸리지 않는다.**
> 그 제한은 "사용자별로 다른 카드"에만 적용된다. 기본 카드를 `update()` 하는 방식은 인원 제한이 없다.

### 투표 토글 규칙

| 상황 | 결과 |
|---|---|
| 처음 클릭 | 그 항목에 투표 |
| 같은 항목 재클릭 | 선택 취소 |
| 단일 선택에서 다른 항목 | 표를 옮긴다 |
| 복수 선택에서 다른 항목 | 둘 다 유지 |

### 마감

두 겹으로 처리한다. 타이머만 믿지 않는다.

1. **타이머** — 생성 시 `asyncio` 타이머를 걸어 마감 시각에 자동으로 닫는다
2. **지연 검사** — 투표가 들어올 때마다 마감 시각을 확인한다.
   프로세스가 재시작돼 타이머가 사라졌어도 첫 상호작용에서 닫힌다

수동 마감은 **만든 사람만** 가능하다 (`from_.id == creator_id` 서버측 검사).
버튼은 모두에게 보이지만 다른 사람이 누르면 거절 안내가 그 사람에게만 간다.

`close_poll` 은 `closed_at IS NULL` 조건부 UPDATE 라 **두 번 닫히지 않는다.**

### 상태 (SQLite)

```sql
polls(id, conversation_id, activity_id, service_url, creator_id, creator_name,
      title, multi_select, closes_at, closed_at, created_at)
poll_options(poll_id, idx, label)
votes(poll_id, option_idx, user_id, user_name, voted_at)  -- PK(poll_id, option_idx, user_id)
```

기본 경로는 `vote-agent/data/votes.db` (`VOTE_DB_PATH` 로 변경 가능).
`service_url` 은 재시작 후 카드를 갱신하려면 반드시 필요하다.

### 제약

| 항목 | 값 | 이유 |
|---|---|---|
| 항목 수 | 2~10개 | 카드 본문 28KB 제한 + 버튼 과다 방지 |
| 제목 | 80자 | 매니페스트/카드 가독성 |
| 항목 이름 | 60자 | 버튼 제목 가독성 |
| 투표자 이름 표시 | 15명까지, 이후 `+N명` | 카드가 넘치는 것을 막는다 |

### 엣지 케이스

| 조건 | 동작 |
|---|---|
| 항목 1개 / 11개 이상 / 중복 | 거절, 폼은 값 보존하며 유지 |
| 마감 표현 해석 실패 | 거절, 무엇을 이해하지 못했는지 표시 |
| 없는 투표에 클릭 (DB 유실 등) | "찾을 수 없습니다" 안내 |
| 마감 후 클릭 | 카드를 마감판으로 갱신하고 안내 |
| 만든 사람 아닌 사람이 마감 | 거절, 만든 사람 이름 안내 |
| 이미 마감된 투표 재마감 | 무시 |
| 같은 activity 재전송 | `activity.id` seen-set 으로 무시 |

## 클라우드 이전 전 감사 (2026-08-20)

### 보관되는 데이터

| 저장소 | 내용 | 민감도 |
|---|---|---|
| `votes.db` › `polls` | `conversation_id`, `activity_id`, `service_url`, `creator_id`(AAD MRI), **`creator_name`(실명)**, 제목, 마감 시각 | 개인정보 |
| `votes.db` › `poll_options` | 항목 라벨 | 낮음 |
| `votes.db` › `votes` | `user_id`(MRI), **`user_name`(실명)**, 항목, 투표 시각 | **개인정보 + 선호 정보** |
| 프로세스 메모리 | activity id, 대화방 id, 락, 타이머 | 식별자만 |
| roulette | **아무것도 저장하지 않는다** (30초 작업, 메모리에 activity id 뿐) | — |

**누가 무엇에 투표했는지**가 평문으로 남는다. 민감한 주제의 투표라면 그 자체가 민감 정보다.
클라우드에서는 이 파일이 플랫폼 스토리지(App Service `/home`, 볼륨 등)에 놓이므로
백업·스냅샷 정책도 함께 따라온다.

### 보존정책 — 자동 삭제된다

| 대상 | 기본 보존 | 환경변수 |
|---|---|---|
| 마감된 투표 | **1일** | `VOTE_CLOSED_RETENTION_DAYS` |
| 마감 없이 방치된 투표 | **30일** | `VOTE_OPEN_RETENTION_DAYS` |

`poll_options`·`votes` 는 `ON DELETE CASCADE` 로 함께 사라진다.
정리 시점은 **프로세스 기동 시**다.

마감 후 1일이면 충분한 이유 — 채팅방의 마감 카드는 **그냥 메시지**라 DB 없이도 계속 보이고,
버튼이 사라져 있으므로 다시 그릴 일이 없다. 1일은 마감 시점 갱신이 네트워크 오류로
실패했을 때 복구할 여유를 남기기 위한 것이다.

`VOTE_CLOSED_RETENTION_DAYS=0` 으로 두면 다음 기동 시 마감분이 전부 사라진다.

### 로그

투표 로그는 실명 대신 **사용자 id 의 8자 해시**를 남긴다
(`투표 poll=abc123 idx=1 user=9ebbc7de`). 같은 사람인지 구분은 되지만 신원은 드러나지 않는다.

**왜** — 클라우드 로그는 플랫폼 저장소(Log Analytics 등)로 흘러가고 보존 기간이
우리 통제 밖이다. 실명을 남기면 개인정보가 통제 밖으로 나간다.

### 동시성 — 실제로 돌려서 확인함

| 상황 | 결과 |
|---|---|
| 같은 대화방에서 5명이 동시에 `@당첨자뽑기` | **1건만 진행, 4건 "진행 중" 거절.** 연출이 겹치지 않음 |
| 다른 대화방 5곳에서 동시에 | 5곳 모두 독립 완주, 결과 안 섞임 |
| 같은 activity 가 동시에 두 번 도착 | 1건만 처리 |
| 같은 투표에 20명 동시 클릭 | **20표 전부 기록, 유실 0.** A 10 / B 10 정확 |
| 한 사람이 같은 항목 20번 연타 | 최대 1표 (PK 제약 + 토글) |
| 5개 대화방 × 3명 동시 투표 | 방마다 정확히 3표, 표가 안 섞임 |
| 투표와 마감이 동시에 | 마감 1회만 적용, 마감 후 표는 기록되지 않음 |

**동작 원리** — 단일 이벤트 루프에서 `_running`(대화방별)·`_locks`(투표별)로 직렬화한다.
락 확인과 등록 사이에 `await` 가 없어 원자적이고, 카드 갱신도 락 안에서 하므로
갱신 순서가 뒤바뀌지 않는다.

### ⚠️ 클라우드 제약: **반드시 인스턴스 1개로 고정해야 한다**

`_seen`·`_running`·`_locks`·`_timers` 는 **프로세스 메모리**에만 있고
`votes.db` 는 **로컬 파일**이다. 복제본이 2개 이상이면:

| 상태 | 복제본 2개일 때 |
|---|---|
| `_seen` | 재전송이 다른 복제본에 가면 **연출 2번 실행** |
| `_running` | 같은 대화방에서 **추첨 2건 동시 진행** |
| `_locks` | 같은 투표에 동시 클릭 시 **갱신 순서 역전** |
| `_timers` | 마감 타이머가 **중복 발화** |
| `votes.db` | 복제본마다 다른 파일 → **투표가 절반씩 나뉜다** |

설정:

| 호스팅 | 설정 |
|---|---|
| App Service | 스케일 아웃 **1** 고정, `WEBSITE_DISABLE_OVERLAPPED_RECYCLING=1` |
| Container Apps | `minReplicas=1`, **`maxReplicas=1`** |
| Container/VM | 컨테이너 1개 |

DB 는 **재시작 후에도 유지되는 경로**에 두어야 한다 (`VOTE_DB_PATH`).
App Service 는 `/home/...` (Azure Files), Container Apps 는 마운트한 볼륨.
컨테이너 기본 파일시스템에 두면 재시작마다 진행 중인 투표가 사라진다.

여러 복제본이 필요해지면 상태를 외부로 빼야 한다 (Redis 락 + Postgres). 지금 규모에는 과하다.

**roulette** (실측 페이로드 + 실측 로스터)

- 평문 토큰 해석 8케이스 (완전일치·접두사·동명이인 모호·미존재)
- `@모든 사용자` 페이로드 → 전원 모드, 후보 10명
- 쪼개진 멘션 3조각 → 후보 1명, 이름은 로스터 전체 이름
- 봇만 태그 → 전원 모드 오인 없음, 후보 0명
- 라운드 수식 N=2~30 × 모든 n (464조합) → 불변식 위반 0건
- 실제 시계 타이밍: 편집 간격 1.0초 이상, 초당 0.83회, 메시지 1개 유지

**vote**

- 마감 표현 13종 + 애매한 입력 6종 거절 + 연도 이월 4종
- 저장소: 토글·이동·취소·복수선택·동표·중복마감 방지

- 마감 권한, 지연 검사(타이머 유실 시), 실제 1초 타이머 자동 마감
